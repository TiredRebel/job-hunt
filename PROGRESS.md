## 2026-07-21 (2) — Jobs-count reconciliation surfaced

OpenSpec `sources-jobs-count-discrepancy` proposed and fully implemented
(all 44 tasks): the Sources page's per-run "found/new" counters and the
Jobs dashboard's `total` count now share an explicit reconciliation view,
closing the silent gap between `scraper.jobs_raw` and `core.jobs` that was
the original user-reported confusion. **Gateway**: new read-only
`reconciliation` module — `GET /v1/reconciliation/sources` (per-source
buckets `raw / processed / pending / failed / visible / hidden` from a
single `GROUP BY` SQL query joining `core.sources` LEFT JOIN
`scraper.jobs_raw` LEFT JOIN `core.jobs`), `GET /v1/reconciliation/jobs`
(cross-source aggregate + `legacyDelta`), and `GET /v1/reconciliation/dead-letter`
(a public, dashboard-facing mirror of the internal-token-guarded
`GET /v1/automation/jobs/dead-letter` — discovered during live
verification that the automation endpoint couldn't be called from a
browser; the new public mirror reuses the existing `ScraperClient`
injected into `ReconciliationService`). No migrations, no schema changes.
**Web**: `SourcesPageClient`/`SourceRow` render a per-source cumulative
jobs-health summary line (`Discovered / Processed / Pending / Failed /
Hidden`, labeled "Across all runs" to distinguish from the per-run
counters); `JobsDashboardSummary` renders a secondary reconciliation strip
under the existing metrics row, with `failed` deep-linking to a new
`/[locale]/jobs/dead-letter` route when non-zero, the whole strip hidden
on a fresh install (`discovered=0`), and graceful degradation when any
endpoint fails. New `lib/api/reconciliation.ts` + `lib/api/automation.ts`
typed clients; localized keys added under `sources.jobsSummary.*`,
`jobs.dashboard.reconciliation.*`, and `jobs.deadLetter.*` in both
`en.json` and `uk.json`. OpenAPI + `shared-ts` client regenerated (3 new
operations, 3 new schemas). Gates green throughout (api 147/147 vitest +
tsc + eslint + build; web tsc + eslint + build clean, vitest tests pass —
the pre-existing coverage-gate failure on `src/lib/**` function coverage
is unchanged from master and not caused by this change). Live-verified
against the rebuilt Docker stack: triggered a real scrape run on `dou`
and watched `rawTotal` go from 148 → 151 and `pending` update accordingly;
the actual discrepancy the user asked about is now visible at a glance
(dou: 151 raw / 3 visible / 147 pending / 1 failed; workua: 64 raw / 0
visible / 64 pending). 3/3 new Playwright regressions pass; the 2
pre-existing `board-reorder.spec.ts` failures are data-state issues
(need 3 saved-stage seeded jobs), confirmed present on master before
this change. Not committed — awaiting explicit go-ahead per repo
convention.
